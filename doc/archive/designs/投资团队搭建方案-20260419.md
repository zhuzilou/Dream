# 投资团队搭建方案

**日期：2026年4月19日**
**核心定位：让 Frank 能力更强 → 赚钱**

---

## 一、核心定位

### 1.1 根本目标
**赚钱。**

产品团队和投资团队是两条独立的事业线：
- 产品团队 → 做出产品 → 赚钱
- 投资团队 → 让钱生钱 → 赚钱

### 1.2 Frank 的定位
Frank 是一个 Agent，能力有边界。

不是要"建团队"，而是要**给 Frank 配备更好的工具和扩展件**，让他能做的事情更多、更高效。

---

基于 Muse 的讨论和案例研究，Frank 当前和未来的能力缺口：

| 缺口 | 严重程度 | 现有解决方案 | 优先级 |

| **风控辅助** | 高 | 待定 | P1 |

## 三、参考案例

### 3.1 Zero Point Team（ZPT）

**运作模式：**
- 多 Agent 协作网络：信号 Agent → 风险 Agent → 执行 Agent
- 投票机制：信号需要风险 Agent 通过才能执行
- 主动推送（push-based）：检测到变化立即触发后续流程

**局限性：**
- 信号 Agent 质量决定整个系统上限
- 多 Agent 协调带来延迟
- 高度依赖个人判断 → 仍是单点风险

### 3.2 量化基金实践（Two Sigma、Man Group、DE Shaw）

| 基金 | AI 应用 | 关键洞察 |
|------|---------|---------|
| **Man Group ATHOS** | 多 Asset Class 专属 Agent + 中央 Meta-Agent | AI 自主决策不超过 20%，人类仍是主导 |
| **DE Shaw** | Scout → Diagnostician → Alerter 三层架构 | 分层设计，每层有明确输入输出 |
| **AQR** | LLM 研究助手 + 人工审核 | AI 生成 → 人类把关 |

**核心结论：成功的 AI 投资系统都有一个共同点——人类始终保留最终决策权。**

### 3.3 失败案例警示（Basis Thinking 2023）

- 完全自主的多 Agent 系统在 2023 年银行业危机中未能及时响应
- 教训：**缺乏 Human-in-the-loop 机制的系统是危险的**

## 四、三种方案对比

### 方案 A：Frank 为核心的单人决策体系

**架构：** Frank 全权决策，Agent 作为信息工具辅助。

**优点：**
- 决策效率高，无协调成本
- 符合现有团队文化，过渡成本低

**缺点：**
- 单点失败风险高
- Frank 精力上限即团队天花板
- 难以规模化

**适用场景：** 小规模试水，Frank 兼具研究和执行能力。

---

### 方案 B：双人制衡体系（Frank + 风控/第二分析师）

**架构：** Frank 决策 → 第二人审核风险 → 执行。

**优点：**
- 有效降低单点失败风险
- 风控审查系统性降低重大亏损
- Frank 休假时有备份

**缺点：**
- 决策效率下降（多一层审核）
- 需要找到可靠的第二人

**适用场景：** 规模扩大后，需要风控兜底。

---

### 方案 C：基金模式（多 Agent 专业化分工）

**架构：** Frank + 新闻收集员 + 风控 Agent + 量化 Agent。

**优点：**
- 专业分工，各司其职
- 系统可扩展性强

**缺点：**
- 协调成本高
- 需要更多人力维护
- 对初期阶段过于复杂

**适用场景：** 长期目标，规模化运营。

---

## 五、推荐路径

### 近期（1-3个月）：方案 A 起步

**目标：验证 Frank + 新闻收集员 的协作模式**

| Agent | 职责 |
|-------|------|
| Frank | 首席分析师 + 最终决策者 |
| 新闻收集员 | 信息采集 + 结构化输出 + 框架执行 |

**工作流：**
1. 新闻收集员主动推送结构化新闻卡片给 Frank
2. Frank 按需检索（不受关键词限制）
3. Frank 反馈 → 新闻收集员优化
4. 每周一次过滤效果报告

---

### 中期（3-6个月）：方案 B 过渡

**目标：引入风控意识，但不设专门风控人**

- 在新闻收集员的推送中增加"风险提示"字段
- Frank 自己定义止损规则，Agent 提醒
- 慢慢建立决策的规则化、显性化

---

### 长期（6个月+）：方案 C 扩展

**目标：建立可独立运转的投资能力**

- 引入专门的风控 Agent
- 引入量化分析 Agent
- Frank 专注于最终的判断和决策

## 六、Muse 的关键质疑与解答

### 质疑1：9528 的角色是什么？
**原质疑：** 协调层对投资团队内部流程没有实质贡献。

**解答：**
- 9528 在投资团队中的定位：**协调和通信**
- 不干预 Frank 的决策
- 负责跨团队通信（如果需要）
- 负责流程记录和归档

**实际意义：** 9528 是"秘书"而非"经理"，不拍板，只执行协调事务。

---

### 质疑2：三层架构实际是两层
**原质疑：** Layer 1 + Layer 2 都是新闻收集员，Frank 只做 Layer 3。

**解答：**
- 这个质疑是对的。收集员确实是执行者，Frank 是决策者
- 但这本身不是问题——**分工本身就是如此**
- Frank 定义框架（关键词池、分类标准）
- 收集员执行框架（采集、过滤、呈现）
- Frank 做最终判断

**关键：** Frank 不能只做判断，需要参与框架的定义和调整，否则系统会偏离他的实际需求。

---

### 质疑3：AI 替代假设未验证
**原质疑：** 没有指定工具、接入方式、质量验证。

**解答：**
- **工具选型：** 新闻收集员 skill 采用 timor.tech API + 财联社/东方财富爬虫
- **质量验证：** 通过 Frank 的反馈来验证（推送有用 vs 无用）
- **落地：** skill 已有完整方案，见 `trading-calendar.skill` 的模式

---

### 质疑4：没有风控节点
**原质疑：** 没有止损条件、决策边界、复盘机制。

**解答：**
- 这个问题在近期方案中确实未完全解决
- **中期方案：** Frank 自己定义止损规则，Agent 在推送时提醒
- **长期方案：** 引入风控 Agent，有一票否决权
- **近期应对：** 在新闻收集员的推送中增加"关联风险"字段

---

### 质疑5：Frank 不在系统就停
**原质疑：** 不是可独立运转的团队。

**解答：**
- **这恰恰是我们定位的优势，不是问题。**
- 我们的目标不是"建一个不依赖 Frank 的系统"
- 我们的目标是"让 Frank 一个人更强"
- Frank 的判断力是核心价值，无法被替代
- 只要 Frank 在，系统就在

## 七、新闻收集员设计（落地版）

### 7.1 角色定义
- **名称：** Scout（侦察员）
- **定位：** Frank 的信息扩展件，不是独立团队成员
- **输出：** 结构化新闻卡片 + 按需检索

### 7.2 工作流程

```
全量新闻采集 → 存入数据库
      ↓
结构化卡片推送（每日3次：08:30/12:30/18:30）
      ↓
Frank 接收 → 判断 → 反馈（有用/无用/漏了）
      ↓
Scout 记录反馈 → 每周报告优化
      ↓
Frank 随时可查询：最近 X 相关的新闻？
```

### 7.3 反馈机制
- **实时反馈：** Frank 对每条推送回复"有用/无用/关键词补充"
- **周报：** 每周五 Scout 输出"本周推送效果报告 + 下周优化建议"
- **月复盘：** 每月一次 Frank 和 Scout 共同复盘关键词池和分类标准

## 九、结论

**投资团队 = 以 Frank 为核心的能力扩展系统**

- Frank 是最终决策者，不可替代
- 新闻收集员（Scout）是 Frank 的信息基础设施
- 9528 是协调层，不干预决策
- 风控和量化能力是未来的扩展方向

**核心逻辑：赚钱 = Frank 的判断力 + Scout 的信息效率**
